<p>事情是从一个很普通的上午开始的：二十个 Claude 号，其中五个在同一天陆续要求二次验证，另外十五个完全没事。团队第一反应是「IP 段被封了」，准备换服务商。但换之前花半小时查了一下，那五个号用的不是同一条出口，反而是同一份浏览器配置文件。真正的问题不在网络，在隔间没有做全。这篇按实际排查顺序讲清楚：症状怎么读、追问问到哪一层、隔间该隔到什么程度、以及怎么确认一组出状况时没有扩散。</p>
<h2>一、那天上午的实际症状</h2>
<p>五个号的表现并不完全一样，这点很关键。有两个是打开对话页直接跳验证，有两个能进但发消息报错，还有一个是 API 调用返回 429，网页端却正常。三种症状指向的环节不同。</p>
<h3>症状先分三类再看</h3>
<p>跳验证偏身份与设备，页面报错偏网络与地区，API 限流偏调用节奏与配额。三类同时出现，说明共用的环节不止一个，而不是单一出口出了问题。</p>
<h3>为什么另外十五个没受影响</h3>
<p>因为它们分属另外两个批次，用的是不同的浏览器配置目录和不同的支付方式。同样是「一批号」，实际的隔离度差了一整个层级，所以损失被限制在五分之一。</p>
<h2>二、追问一：出口共用了，还是环境共用了</h2>
<p>这是最容易搞混的一步。出口共用会带来地区与延迟上的共性，环境共用带来的则是设备指纹、Cookie、本地存储的共性。两者的排查入口完全不同。</p>
<h3>先把出口这条线排掉</h3>
<p>拉一张表，把五个号的出口 IP、ASN、城市列出来，用 ipinfo.io 批量查一遍。如果五个 IP 分属不同段、不同城市，出口就不是共同点，问题在别处。这一步十分钟能做完，能省掉一次白换服务商。</p>
<h3>再看环境这条线</h3>
<p>查浏览器配置目录。如果五个号共用同一个 Chrome 用户目录，或者虽然分了目录但指纹参数由同一个模板批量生成，那它们在外看就是同一台设备。案例里的情况属于后者：目录分了，但 Canvas、WebGL、字体列表三项参数完全一致，等于没分。</p>

<h2>三、追问二：隔间到底要隔几层</h2>
<p>「独立隔间」这个词听起来抽象，拆开其实只有四层，而且每层都有能验证的落地物。</p>
<h3>四层隔间与各自的责任</h3>
<p>网络层管出口，IP 固定、地区固定、不与他人共用；设备层管浏览器，一个号一个配置目录；身份层管时区、语言、UA 与屏幕参数，跟出口城市对齐；凭据层管登录态与支付方式，密码进密码管理器，卡按号分散。四层里任何一层塌了，整组号就会被算成一源。</p>
<h3>哪一层最容易被省掉</h3>
<p>身份层。因为它看不见，不改也能跑起来，于是被默认忽略。但时区与出口城市不一致这件事，平台侧一眼就能看出来，且不需要任何复杂检测。改起来也最简单，配置目录里改一个参数的事。</p>
<h3>隔到这一层要花多少时间</h3>
<p>按单号算，首次搭环境约十到十五分钟，之后复制模板并改三项参数，约三到五分钟。二十个号半天能做完，比一次集体验证后重新申诉要快得多。</p>
<h2>四、追问三：一组出状况，怎么确认没扩散</h2>
<p>出问题当天最需要的不是立刻修，而是先划出边界：哪些号受影响、哪些没受影响、边界是按什么分的。</p>
<h3>用三个维度切边界</h3>
<p>按批次切（同批是否全中）、按出口切（同段是否全中）、按环境切（同配置目录是否全中）。案例里只有「同配置目录」这一刀切下去全中，另外两刀都有漏网，边界立刻就清楚了。</p>
<h3>扩散的早期信号</h3>
<p>看两件事：未受影响的号在四十八小时内是否出现同类验证，以及新开号是否也走同一条路径。前者说明边界在扩大，后者说明模板本身有问题。两个信号都在，就要先停开号，把模板修好再继续。</p>

<h2>五、把隔间做成可以复制的东西</h2>
<p>修好这一批不难，难的是下一个人接手时不重犯。所以隔间必须落成资产：一份目录结构约定、一份参数对照表、一份异常记录。</p>
<h3>目录结构怎么定</h3>
<p>按「批次/账号编号」两级建目录，每个账号目录里只放浏览器配置与该号的代理设置，凭据单独存在密码管理器。这样打包移交时只交一个目录，不会连带其他号的信息。</p>
<h3>参数对照表里写什么</h3>
<p>四列就够：账号编号、出口城市、时区、界面语言。看起来简单，但这四列能覆盖大部分环境一致性的排查工作。每周核对一次，发现不一致当场改，比出事后回溯省力。</p>
<h3>这套做法解决不了什么</h3>
<p>它解决的是「一组出状况不牵连其他组」，解决不了「号本身的行为是否合规」。环境做得再干净，如果号的使用方式本身有问题，该出的事还是会出。这一点需要在选号、用途和日常节奏上另行把关，不在本文范围内。</p>
<h2>常见问答</h2>
<h3>每个号都单独配浏览器，会不会太占资源？</h3>
<p>答：占，但可控。一个配置目录通常几十到几百 MB，二十个号十个 GB 以内，普通办公机放得下。真吃紧就只给关键号独立目录，辅助号两两合并，但合并的两个号必须错开登录时段，且不能共用支付方式。</p>
<h3>指纹参数要不要每次都随机？</h3>
<p>答：不要。随机化会让同一个号每次登录都像换了台设备，反而更可疑。正确做法是每个号生成一次、长期固定，跟着这个号走到底，只在设备真换的时候成套迁移。</p>
<h3>出口分组和浏览器分组，哪个优先做？</h3>
<p>答：先做浏览器分组。原因很实际：出口可以事后换，配置目录里的历史记录和指纹不会因为换 IP 而改变，先把它理顺，后面换线时边界才清楚。预算只够做一件事时，也是先做这个。</p>
<h3>已经混用很久了，还能拆开吗？</h3>
<p>答：能，但要慢。先拆最关键的几个号，拆完观察一周，没有新的验证再加下一批。一次性全拆会让所有号同时处于「新设备」状态，等于自己制造了一次集体异常。</p>
